Low-code does not mean no logic. It means applying a useful pattern without rebuilding it every time.

The basics · Query habits

Start with good habits

Keep the work focused
  • Filter unneeded rows early.
  • Remove columns you will not use.
  • Preserve query folding where supported.
Keep the query understandable
  • Name steps and group related queries.
  • Disable load for helper-only queries.
  • Check errors, nulls, and unexpected values.
Measure, do not assume. A query reference is not a shared cache. Table.Buffer is not an automatic performance improvement.
Quick check: Use column quality and profiling. Profiling defaults to the first 1,000 rows; switch to the entire dataset when validating.
The basics · Data types

Choose the right types

Meaning comes first
  • Text: identifiers such as 00123.
  • Date / DateTime: keep the time only when needed.
  • True/False: yes/no flags.
Pick the numeric precision
  • Whole number: counts and integers.
  • Decimal number: fractional values; floating-point precision.
  • Fixed decimal: exact values to four decimal places.
Set types explicitly. Review automatic Changed Type steps instead of leaving final columns as Any. Use the correct locale when parsing dates and numbers.
Quick check: Confirm leading zeros survive, dates parse as intended, and type conversions do not introduce errors.

Parameters

Change environments and development filters without editing every query.

Parameters

Same solution. Different environment.

The query logic stays the same across development, test, and production. Only the connection settings change.

Define parametersReplace fixed source settings with values your queries share.
Set the destinationChoose values locally or configure them for the target workspace.
Reuse the logicRefresh against the selected source without rewriting transformations.
Deployment: Set target values manually or through supported deployment rules. Publishing alone does not switch environments; source access must also be configured.
Demo: Compare the baseline College Majors queries with With Parameter. Change Repo and Branch; both queries follow the new settings.
Parameters with functions

Many environments. One shared configuration.

Maintain environment settings outside individual files. Anyone with access can connect to the same shared configuration.

Define centrallyMaintain a shared mapping of approved environments and their settings.
Select locallyEach file uses a parameter to choose its environment.
Retrieve with functionsLook up that environment's settings and use them in the queries.
Update once, reuse on refresh. Keep allowed environment choices in sync, require one matching configuration, and grant access to the mapping and source.
Demo: Select Environment Parameter. Follow EnvironmentMapping through Repository and BranchSelection into both College Majors queries.
Parameters · Development filtering

Filter for development. Not query by query.

Connect your queries to one shared parameter once. Then switch development filtering on or off in one place.

During development
FILTER = true

Work with a smaller dataset across the queries using the parameter.

Ready for full data
FILTER = false

Disable development filtering without removing filter steps from each query.

Set up once. Toggle centrally. Only queries wired to FILTER respond. Validate with full data before publishing.
Demo: Toggle FILTER once. Inspect both Food Survey filter examples; the baseline stays unchanged.
Parameters · More control with another parameter

Same filter. More customization.

Both examples use a parameter to turn filtering on or off. The second adds another parameter so you can choose how many rows to keep.

Start with the switchFILTER controls whether development filtering applies in both examples.
Add a row-count parameterFilterRowCount replaces the fixed limit in the second example.
Adjust in one placeChoose the sample size or turn filtering off without editing query steps.
Less downstream work is not necessarily a smaller download. This CSV example filters after reading the source; it does not demonstrate server-side folding.

Duplicates

Decide which values match and which row stays.

Duplicate keys · Biopics

Distinct in Power Query. Equal in Power BI.

Illustrative valuesPower QueryPower BI model (AS engine)
"Film A"
"FILM A"
"Film A "		Three distinct valuesAll three are the same value
Different comparison rules. Power Query is case-sensitive and preserves leading and trailing spaces unless you remove them. The model ignores casing and removes trailing spaces, but keeps leading spaces.

Leading spaces still matter: " Film A" and "Film A" are distinct in both.

Demo: Compare Biopics - Fact and Biopics - Dimension before and after Remove Duplicates.
Duplicate keys · Keep the display text

Normalize the key. Keep the label.

CopyKeep the original title and create a temporary comparison column.
NormalizeTrim and apply proper case to the helper column.
DeduplicateMatch on the helper, then remove it. The surviving display text stays.
Separate identity from appearance. A matching rule need not overwrite the text your users see.
Demo: Step through Biopics - Dimension-Retain Casing. Compare the original title and title - Copy.
Duplicate rows · Keep a specific row

Which duplicate do you want to keep?

The latest record? The highest-priority source? Sometimes removing duplicates also means choosing a specific winner.

The expectation

Sort the preferred row to the top, then Remove Duplicates keeps that first row.

Sorting alone is not enough

Power Query's evaluation and optimizations do not guarantee that Remove Duplicates preserves the preceding sort order.

A sorted preview is not a retention guarantee. Check which record survives, not just whether duplicates were removed.
Demo: Open Biopics - Sorted Duplicates. Compare the sorted rows with the row retained after Remove Duplicates.
Duplicate rows · The solution

Use the index method

In this tested example, adding an index after sorting preserves the intended row during deduplication.

Sort + add an indexPut the preferred row first, then add the index column.
Remove duplicatesSelect the intended duplicate key, not the index.
Remove the indexDiscard the helper column and check the retained row.
Choose the winner and the matching rule. Define tie-breakers for equal sort values. Combine with the normalized helper key when casing and spaces also need handling.
Demo: Open Biopics - Dimension-Retain Sort, then Retain Casing & Sort to combine both patterns.

Queries as Variables

Think beyond a straight line of steps: nest, branch, and reuse earlier results.

Queries as variables · Thanksgiving Dinner

Steps do not have to form a straight line

The Applied Steps list looks sequential. But each step uses the values it references, not automatically the step immediately above it.

Nest a set of stepsA local variable can contain a complete query and return its result.
Branch from any stepUse an earlier result as the starting point for another transformation.
Reference it againReturn to an older result without passing through every intervening step.
References determine the flow. Bypass a step by referencing an earlier value. Any steps that value depends on are still needed.
Demo: Open Thanksgiving Dinner - Variables within Query. TempQuery contains a whole set of steps; the merge uses its result alongside the full survey.
Queries as variables · Follow the references

Use an earlier result again

A filtered branch does not overwrite its input. The original value is still available to other steps in the same scope.

A whole query in one variable

TempQuery has its own source, filters, and shaping steps. Its final table becomes a value the outer query can use.

An earlier step as another input

Reference Promoted headers for the full survey, even after creating a filtered branch. Merge the full table with the local lookup.

No undo required. Referencing an older step does not delete later steps. It chooses which result to use; it does not guarantee a cached copy.
Demo: In a disposable copy, add a filtered branch after Promoted headers. Have the merge reference Promoted headers again and show that it still receives the full survey.

Refresh Resilience

Handle missing columns and unavailable sources deliberately.

Refresh resilience · Daily Show Guests

A missing column need not change the shape

ExpectDeclare the five output column names.
CompareFind expected names missing from the incoming table.
ShapeAdd missing columns as null, then keep the expected set.
Stable shape is not recovered data. A renamed field is not mapped back; its old name becomes null. Required fields need separate validation.
Demo: In a disposable Column Safety copy, remove or rename a column after Promote Headers. Inspect the missing-column list and output.
Refresh resilience · Source failure

A green refresh can still mean missing data

When the source succeeds

Read the source, promote headers, and shape the expected output.

When the protected expression errors

Return an empty table with the expected columns, then apply the same shaping steps.

Empty is not last-known-good. This fallback can replace loaded rows with no data. It does not log the outage or catch every failure.

Inspect row counts and column quality. Profiling defaults to 1,000 rows; validate the full dataset when needed.

Demo: Trigger a controlled error inside the Source Safety copy's protected expression. Inspect the zero-row result, then restore the source.

Date Tables

Consistent dates, keys, and business rules for DAX and time intelligence.

Date tables · A foundation for DAX

Give DAX a consistent calendar

A date table is more than a list of dates. It gives measures and reports a shared way to define and compare periods.

DatesOne unique, nonblank row per day, with no gaps across the required range.
Keys and sortingRelate facts through the date or date key. Use numeric sort keys for month and period labels.
Business rulesDefine fiscal years, quarters, week starts, and other business periods consistently.
Put the calendar to work. Configure relationships, sort labels, and mark the date table where required. Apply its rules in DAX for YTD, prior-year, and period comparisons.
Demo: Inspect Date Table from AI: Date, Month Number, YearMonthSort, and fiscal fields. Validate the template's January fiscal-year start against the business rules.
Date tables · Follow the fact data

Size the calendar to your data

Another option for smaller models: derive the range from the fact table instead of generating decades of dates you do not need.

Read the fact datesUse a correctly typed date column to find the minimum and maximum.
Build every dayGenerate a continuous calendar, including days with no fact rows.
Allow room to growExtend the boundaries for complete years, fiscal periods, and planning dates.
Match the range to the need. Classic time intelligence needs full-year coverage. On large fact tables, measure the cost of finding boundaries or use a maintained range.
Demo: Date Table from Fact uses the guest data's 1999-2015 range. The saved query uses exact min/max dates; add empty-data handling and any required year or future-date padding.
